## 1. Назначение и цели

Система управляет спортивным залом: администраторы работают в
веб-панели, тренер и клиент — в едином Android-приложении. Система ведёт
клиентов, тренеров, залы, тренировки, шаблоны, питание, замеры веса, отчёты,
чаты, уведомления и push.

Цели:

1. Полный цикл «администратор → тренер → клиент» без бумажных журналов.
2. Единые данные и права для web и mobile.
3. Предсказуемый жизненный цикл тренировки и защита истории от изменений.
4. Готовность к публикации Android-приложения в RuStore.

Границы MVP: офлайн-режим, оплата/абонементы, iOS, конструктор рационов,
вложения в чате и Redis pub/sub для чата — вне объёма.

| Термин | Значение |
| --- | --- |

| Демо-данные | Набор залов/людей/тренировок для проверки и показа |

## 5. Функциональные требования

### 5.1. Аутентификация и сессии

- `POST /auth/login` — телефон + пароль; ответ содержит access/refresh-токены.
  Refresh дополнительно ставится httpOnly-cookie.
- Access JWT — 15 минут, refresh — 30 дней с ротацией.
- `POST /auth/refresh` — принимает cookie или refresh в body. Пустой refresh →
  401 без отзыва остальных сессий.
- `POST /auth/logout` — отзывает refresh и очищает cookie.
- `POST /auth/change-password` — смена своего пароля, отзыв всех refresh.
- `POST /auth/reset-password` — ADMIN/ADMINISTRATOR (свой зал), отзыв всех refresh.
- `GET /auth/me` — профиль пользователя.
- `PATCH /auth/timezone` — IANA-пояс пользователя.
- `PATCH /auth/push-token` — FCM-токен.
- Cookie: `HttpOnly`, `SameSite=Strict`, `Secure` только при HTTPS
  (`X-Forwarded-Proto`/`request.secure`), TTL 30 дней.
- Throttle логина — 10 попыток/мин на инстанс (Redis, при недоступности —
  in-memory).
- Архивный тренер не может войти и обновить токен.
- Mobile поддерживает только `TRAINER` и `CLIENT`; иная роль → очистка токенов
  и сообщение «Роль пользователя не поддерживается».

### 5.2. Web-admin — ADMIN

- CRUD залов: название, адрес, активность; `isActive` информационный.
- CRUD тренажёров в зале: название, тип, min/max (min ≤ max), фото, описание.
- CRUD упражнений: название, тип, группа мышц, требует оборудование, видео,
  описание; удаление — soft delete.
- CRUD продуктов питания: КБЖУ ≥ 0.
- CRUD целей (глобальный справочник).
- CRUD клиентов: телефон, имя, пол, рост, дата рождения, стартовый вес и % жира,
  цель, заметки; `startWeight`/`startFatMass` неизменяемы; `passwordHash` не
  отдаётся.
- CRUD тренеров; удаление — архивация с сохранением истории.
- CRUD администраторов с привязкой к залу.
- Связи клиент↔тренер↔зал: создание, деактивация, `assignedBy`.
- Замеры веса любого клиента.
- Сброс паролей клиентов/тренеров/администраторов.
- Загрузка фото: jpg/png/webp ≤ 5 MB, раздача `/uploads/*`.
- Рассылка уведомлений: заголовок, текст, опционально зал; получатели — клиенты
  с активной связью в зале.
- Чаты 1:1 с клиентами и тренерами.
- Глобальные и зальные шаблоны тренировок.
- Отчёты: посещаемость, использование оборудования, по тренерам, вес,
  упражнения.
- Настройки сервера: порт, сертификат, демо-данные.
- UI: универсальный поиск по таблицам, ленивые маршруты (code-splitting).

### 5.3. Web-admin — ADMINISTRATOR

- Видит только свой зал; чужие данные → 403/404.
- Клиенты своего зала: список, создание, редактирование, фото.
- Тренеры своего зала: список, создание, редактирование, фото.
- Связи клиент↔тренер своего зала (`assignedBy=ADMINISTRATOR`).
- Замеры веса клиентов своего зала.
- Сброс паролей клиентов/тренеров своего зала.
- Шаблоны только своего зала (глобальные не видит).
- Входящие уведомления и отметка о прочтении.
- Фильтрация выполняется в Prisma, не в памяти.

### 5.4. Mobile — TRAINER

- Одно приложение на тренера и клиента; интерфейс по роли.
- Главный экран: вкладки «Календарь» (по умолчанию) и «Мои клиенты».
- Календарь месяца: число тренировок по дням, «9+», переход к дню, возврат к
  текущему месяцу.
- День: ФИО, время, зал, статус; сортировка по времени; кнопки по статусу.
- Клиенты: только активная связь; поиск по ФИО; **телефон клиента не
  отдаётся и не показывается**.
- Карточка клиента: «Тренировки», «Прогресс», «Питание», «Вес», «Чат».
- Тренировки клиента: фильтр по периоду, по умолчанию — «Текущая неделя»
  (Пн–Вс по TZ пользователя).
- Создание тренировки: клиент → зал (только залы тренера) → шаблон или с нуля →
  упражнения/тренажёры → вес/подходы/повторы → дата → отправка.
- Дата в прошлом по поясу клиента запрещена; несколько тренировок в день
  разрешены; после создания — `PLANNED`, push клиенту.
- Шаблоны: глобальные + шаблоны своих залов + личные; личные — CRUD; чужие и
  глобальные только применять. Лимит 10 личных, архивация освобождает слот,
  поиск по названию.
- Прогресс: динамика веса/жира, сводка упражнений, график план/факт.
- Питание: назначение и архивация; активные/архив.
- Замеры веса: активная связь.
- Чат с клиентом; блокировка по правилу 6.3.
- Завершение тренировки только из `IN_PROGRESS`, фиксация факта, push клиенту.
- Настройки: профиль, TZ, залы (просмотр), версия/сервер, смена пароля, выход.

### 5.5. Mobile — CLIENT

- Календарь тренировок (месяц, листание, отметки, легенда статусов).
- Тренировка дня: план, старт, чек-лист, факт веса/повторов, комментарий,
  завершение.
- Старт — только из `PLANNED`, только в день тренировки или будущую дату, если
  предыдущая не блокирует. `MISSED` не блокирует следующую.
- После терминального статуса — только чтение; свободное листание всех заданий
  без сохранения и без блокирующих попапов.
- Питание: активные/архивные, только просмотр.
- Отчёты: вес/жир, прогресс по упражнению, сводка; экспорт PDF по периоду.
- Вкладка «Тренировки»: все тренировки с фильтрами по статусу и периоду
  (по умолчанию — текущая неделя; всё время, этот месяц, прошлый месяц,
  3 месяца); тап открывает единый read-only экран.
- Чаты: тренер и администрация; блокировка по правилу 6.3.
- Залы: список залов и тренеров, выбор тренера (`assignedBy=CLIENT`), отвязка.
- Уведомления: при запуске баннер «У вас N новых уведомлений» и счётчик
  непрочитанных; фильтры по типам (тренировки, сообщения, чаты, питание,
  системные); тап ведёт в раздел; отметка о прочтении.
- Настройки: профиль, TZ, версия/сервер, смена пароля, выход.
- При выходе очищаются все пользовательские кеши и провайдеры.

### 5.6. Сквозные модули

**Замеры веса.** Вес (кг), % жира, дата/время, комментарий. Создание: тренер
при активной связи; ADMIN — любой клиент; ADMINISTRATOR — только свой зал.
Просмотр — по правам роли.

**Питание.** Тип `DAILY`/`POST_WORKOUT`, КБЖУ, комментарий, период действия,
`isActive`/`archivedAt`. Назначает и архивирует только тренер; push при
назначении.

**Отчёты.** Динамика веса и % жира; прогресс по упражнению (план vs факт,
fallback серым/пунктиром); сводка «начал X → сейчас Y, N записей»;
посещаемость; использование оборудования; по тренерам. Тяжёлые отчёты — только
за период. Агрегация в PostgreSQL (`groupBy`/SQL), без выгрузки всех строк.
PDF: `GET /reports/pdf/weight`, `GET /reports/pdf/exercises`, кириллица
(DejaVuSans), `Content-Disposition: attachment`, период по умолчанию — неделя.

**Чат.** REST + Socket.IO namespace `/chat`, JWT. История — постранично.
Список чатов: собеседник, последнее сообщение, время, непрочитанные.
1:1: клиент↔тренер, клиент↔админ, тренер↔админ. Общего чата нет.

**Уведомления.** Inbox и отметка о прочтении для всех аутентифицированных
ролей. События тренировок (`WORKOUT`), сообщений/чатов (`MESSAGE`/`CHAT`)
и питания (`NUTRITION`) сохраняются в inbox с `entityId` (переход в раздел);
ручные рассылки — `SYSTEM`, только ADMIN. Push FCM: назначение тренировки,
новое сообщение, назначено питание, напоминание за 1 час, автозакрытие,
завершение тренером, авто-пропуск. При запуске mobile — баннер о
непрочитанных и счётчик в колокольчике.

**Загрузка файлов.** Фото тренажёров/клиентов/тренеров, ≤ 5 MB, volume
`./uploads`.

### 5.7. Backend и служебные модули

- Глобальный префикс `/api/v1`; Swagger UI `/api/docs`, JSON `/api/docs-json`
  (управляется `ENABLE_SWAGGER`).
- `GET /health` → `{"status":"ok"}`.
- `GET/PATCH /admin/server/settings` — порт, активный порт, `restartRequired`,
  данные сертификата.
- `POST /admin/server/certificate` — загрузка пары cert/key (PEM, ≤ 1 MB,
  проверка срока и соответствия), `POST .../certificate/reset` — сброс на
  встроенный.
- `GET /admin/demo/status`, `POST /admin/demo/load`, `DELETE /admin/demo`.
- Seed идемпотентен: админ из env, дефолтная конфигурация, пароли/TZ не
  перезаписываются.

## 6. Бизнес-правила

### 6.1. Жизненный цикл тренировки

| № | Из | Событие/условие | В | Инициатор | Побочные эффекты |
| --- | --- | --- | --- | --- | --- |
| T1 | — | Тренер создал тренировку | `PLANNED` | Тренер | Push клиенту |
| T2 | `PLANNED` | «Приступить» (день тренировки/будущее, предыдущая не блокирует) | `IN_PROGRESS` | Клиент | `startedAt`, таймер 2 ч |
| T3 | `IN_PROGRESS` | «Завершить» | `COMPLETED` | Клиент | Фиксация факта, read-only |
| T4 | `IN_PROGRESS` | «Завершить» | `COMPLETED` | Тренер | Фиксация факта, push клиенту |
| T5 | `IN_PROGRESS` | Прошло 2 ч от `startedAt` | `AUTO_CLOSED` | Система | Факт = план, push клиенту и тренеру |
| T6 | `PLANNED` | 00:00 следующего дня по TZ клиента | `MISSED` | Система | Push клиенту; следующую не блокирует |
| T7–T9 | терминальные | — | — | — | Только чтение |

Запрещено: `PLANNED→COMPLETED`, `PLANNED→AUTO_CLOSED`, `MISSED→IN_PROGRESS`,
любой переход из терминального, назначение на прошлую дату.

- Автозакрытие: фоновая проверка раз в минуту + при старте backend.
- Авто-пропуск: проверка по часовому поясу клиента.
- Параллельные `IN_PROGRESS` не ограничены.
- `PUT` тренировки разрешён только в `PLANNED`, иначе 409.
- Изменение результатов в терминальном статусе → 400
  «Результаты завершённой тренировки изменять нельзя».
- Напоминание за 1 час до `startTime` — однократно (`reminderSentAt`).
- `autoFinishAt = startedAt + 2 ч` в ответе API.

### 6.2. Fallback план → факт

Если фактический вес/повторы не введены, в отчётах
`actualWeight = plannedWeight`, `actualReps = plannedReps`,
`isActualFallback = true` (точка серая/пунктирная).

### 6.3. Блокировка чата

Обе стороны не могут писать, если выполняется хотя бы одно:

1. нет активной связи клиент↔тренер;
2. нет будущих тренировок и последняя тренировка старше 10 дней;
3. истории тренировок нет вовсе.

Будущая тренировка разблокирует чат. Блокировка действует в UI и API.

### 6.4. Шаблоны

- `GLOBAL`: `gymId=null`, `trainerId=null`; создаёт ADMIN.
- `GYM`: `gymId!=null`; ADMIN — любой зал, ADMINISTRATOR — свой.
- `PERSONAL`: `trainerId!=null`; создаёт/правит тренер.
- TRAINER видит глобальные + шаблоны своих активных залов + личные.
- ADMINISTRATOR глобальные не видит; чужой зал → 404.
- Лимит 10 личных; архивация освобождает слот; поиск по названию.
- Soft delete: `isActive=false`, `archivedAt=now()`; история сохраняется.
- Изменение/удаление личного шаблона — только владелец.

### 6.5. Приватность и безопасность данных

- Телефон клиента не отдаётся тренеру ни в одном ответе/экране.
- `passwordHash` никогда не попадает в ответы.
- Пароли — только из `DEFAULT_CLIENT_PASSWORD` при создании; сброс выдаётся
  один раз.
- Смена/сброс пароля и архивация тренера отзывают все refresh-токены.
- API не принимает `role`/`isActive` от клиента там, где это повышает права.
- Логи не содержат паролей, токенов и персональных секретов.

### 6.6. Пагинация

- Query: `page` с 1, `limit` по умолчанию 20, максимум 100.
- Ответ: `{ items, total, page, limit }`.
- `page=0` или `limit>100` → 400.
- Применяется к клиентам, тренерам, тренировкам, чатам, уведомлениям
  (ADMIN/ADMINISTRATOR/TRAINER/CLIENT — по соответствующим спискам).
- Фильтры (зал, клиент, период, статус, поиск) комбинируются с пагинацией.
- Web-admin/mobile запрашивают `limit=100`; UI-переключатели страниц —
  допустимое улучшение, не блокирующее MVP.

### 6.7. Время и часовые пояса

- Все `DateTime` — `timestamptz` UTC; `Workout.date` — `date`.
- Отображение и автоматика — в `User.timezone`; по умолчанию
  `Asia/Novosibirsk` (`DEFAULT_TIMEZONE`).
- Смена TZ пересчитывает календарь, тренировки, питание, уведомления.
- Периодные фильтры тренера и клиента по умолчанию — «Текущая неделя»
  (Пн–Вс по TZ пользователя); в отчётах web и PDF — текущая неделя.
- Единицы: вес — кг, рост — см, жир — %, возраст — из `birthdate`.

### 6.8. Мягкое удаление

- Тренер: `isActive=false`, `archivedAt`; вход/refresh запрещены; связи
  деактивируются; история тренировок/замеров/чатов/рекомендаций сохраняется;
  телефон остаётся занятым; restore не предусмотрен.
- Упражнение/шаблон: `isActive=false`, `archivedAt`; история сохраняется.
- Зал: `isActive` информационный.

### 6.9. Seed и демо-данные

- Seed идемпотентен: не перезаписывает `passwordHash`/`timezone`; обновляет
  роль/имя; создаёт админа из env.
- Дефолтная конфигурация: 34 упражнения, 22 популярных тренажёра в каждый
  существующий зал (без дублей по имени), 3 глобальных шаблона:
  «Вес вверх» (`weight-up`), «Вес вниз» (`weight-down`), «Тонус» (`tone`).
- Демо: 3 зала, 6 тренеров, 20 клиентов, 3 администратора
  (`+79995550201`–`+79995550203`), 780 тренировок, 260 замеров,
  40 рекомендаций, 24 демо-упражнения, 12 демо-шаблонов.
- Пароль демо-пользователей — `DEFAULT_CLIENT_PASSWORD`.
- `clear()` не удаляет дефолтную конфигурацию.
- Новые залы не наполняются тренажёрами автоматически — нужен повторный
  seed/демо (известное ограничение).

### 6.10. Кэш и троттлинг

- Redis: распределённый throttler + кеш.
- TTL: справочники 300 с, отчёты 60 с; ключ отчёта включает пользователя, роль
  и параметры.
- Инвалидация после успешных POST/PUT/PATCH/DELETE через глобальный
  interceptor; демо-операции сбрасывают справочники и отчёты.
- Redis недоступен → in-memory throttler и no-op кеш; API продолжает работать.
- Namespace `REDIS_KEY_PREFIX` (в тестах уникален на процесс).
- Web-admin кэширует профиль (без токенов) в `localStorage` на 10 часов;
  access-токен — только в памяти; refresh — httpOnly-cookie.

## 12. Мобильное приложение

### 12.1. Адрес API

- Базовый адрес: **`https://demogym.staff-rf.ru:3000`**.
- Путь `/api/v1` добавляется автоматически нормализатором; в коде хранится
  только хост/база.
- Нормализация: при отсутствии схемы добавляется `https://`, удаляются
  завершающие `/`, добавляется `/api/v1`.
- Сохранённый старый адрес заменяется при смене версии конфига
  (`currentApiConfigVersion`); после миграции ручной выбор сохраняется.
- Адрес можно переопределить при сборке:
  `--dart-define=API_URL=https://demogym.staff-rf.ru:3000`.
- В приложении доступен экран «Адрес сервера» (вход/настройки).
- PDF и файлы загружаются с того же хоста.

### 12.2. Идентификация и версия

- applicationId/namespace: `com.gymapp.gym_trainer`.
- Версия: `1.0.8+9` (versionName `1.0.8`, versionCode `9`) — минимум.
- Разрешения: `INTERNET`, `POST_NOTIFICATIONS`.
- `usesCleartextTraffic=true` допускается для локальной отладки; боевой адрес
  только HTTPS.

### 12.3. Сеть и сертификаты

- Dio: connect timeout 15 с, receive 30 с; отдельный Dio для refresh.
- HTTPS через `SecurityContext.defaultContext`.
- При невалидном сертификате — диалог «Невалидный сертификат»
  («Принять»/«Отмена»). После «Принять» хост `host:port` сохраняется в
  `flutter_secure_storage` (`trusted_certificate_hosts`), запрос повторяется.
- Доверие только сохранённым хостам; параллельные запросы дедуплицируются.
- При отказе — обычная сетевая ошибка.
- Осознанное ослабление TLS допускается только для доверенного стенда.

### 12.4. Подпись и сборка

- Release подписывается release-ключом (не debug).
- Keystore: `/opt/compose/keyAPP/app-key.keystore` (вне git).
- Параметры — в `mobile/android/key.properties` (в `.gitignore`):
  `storeFile`, `storePassword`, `keyAlias`, `keyPassword`.
- `build.gradle.kts` подключает `signingConfigs.release`; при отсутствии
  `key.properties` допускается debug только для локальной отладки.
- Сборка:
  `flutter build apk --release --dart-define=API_URL=https://demogym.staff-rf.ru:3000`
  и `flutter build appbundle --release ...`.
- Артефакты: `mobile/build/app/outputs/flutter-apk/app-release.apk`,
  `mobile/build/app/outputs/bundle/release/app-release.aab`.
- Проверка: `apksigner verify --print-certs`, versionCode/versionName,
  наличие нового хоста в `libapp.so`, отсутствие старых хостов.
- Инструкция по ключам и RuStore — `docs/RUSTORE_KEY.md`.

### 12.5. Публикация

- Для AAB в RuStore загружаются ZIP-подпись (PEPK) и PEM-сертификат ключа
  загрузки; RuStore подписывает APK своим ключом подписи приложения.
- Для ОС Аврора (при необходимости) — отдельный сертификат разработчика:
  ключ ГОСТ 34.10-2012 и CSR (см. `docs/RUSTORE_KEY.md`).
- Changelog и versionCode инкрементируются в каждом релизе.

## 14. План приёмки

### 14.1. Условия входа

- `make up`, миграции и seed применены; `/health` = 200.
- Собраны backend, web-admin, mobile.
- Есть тестовые пользователи всех четырёх ролей.

### 14.2. Критерии приёмки MVP

1. `make up && make migrate && make seed` поднимает стек; `/health` → ok;
   Swagger доступен.
2. ADMIN входит, создаёт зал → тренажёр с фото → упражнение → продукт →
   тренера → клиента (все поля) → связывает клиента с тренером и залом.
3. TRAINER входит по выданному паролю, видит клиента (без телефона), создаёт
   замер, тренировку (шаблон/с нуля), назначает питание.
4. CLIENT входит, видит тренировку в календаре, стартует, отмечает факт,
   завершает, видит питание и отчёты.
5. Смена/сброс пароля работают; старый refresh и старый пароль → 401.
6. Отчёты веса/упражнений возвращают корректные точки; fallback помечен.
7. Уведомление с `gym_id` приходит клиентам с активной связью в зале.
8. Inbox и прочтение доступны аутентифицированным ролям.
9. Клиент сам выбирает тренера (`assignedBy=CLIENT`).
10. ADMIN/ADMINISTRATOR добавляют замеры (администратор — только свой зал).
11. Пагинация всех списков работает по контракту.
12. Архивный тренер не входит; история сохранена.
13. E2E на отдельной БД `gym_test` зелёные (целевые наборы).
14. Мобильное приложение собирается, подписано release-ключом, все запросы
    идут на `https://demogym.staff-rf.ru:3000`.
15. D2/D3: терминальные тренировки листаются полностью, read-only, без
    попапов; из карточки клиента открывается единый экран.
16. D4: регресс статусов/автоматики/шаблонов/чата/питания/PDF/push пройден.

## 17. Реестр дефектов и предотвращение регрессий

| Дефект | Причина | Исправление | Контроль |
| --- | --- | --- | --- |
| bug1: тренер без профиля получал «archived» | `!trainer?.isActive` трактовал `null` как архив | `trainer?.isActive === false` | e2e gyms/auth |
| bug2: разлогин web-admin после Ctrl+R по HTTP | `Secure` cookie при `NODE_ENV=production` | `Secure` по `X-Forwarded-Proto`/`request.secure` | auth e2e, ручная проверка cookie |

| bug4: завершённая тренировка листалась только по первому заданию | «Далее» всегда сохранял результат | при `isLocked` листать без сохранения | widget M16/M17, D2 |

Дополнительные меры:

- Не менять статусы/переходы без миграции и обновления ТЗ.
- Не добавлять поля без `@db.Timestamptz`/`@db.Date` и индексов.

  артефактов.
- Не коммитить ключи, `.env`, `server-config/`, `ssl/`, `uploads/`.

## 18. Риски и ограничения

1. Нет регулярного прогона на реальном Android-устройстве (эмулятор в среде
   недоступен) — D1–D4 подтверждаются вручную.
2. Release-подпись исторически была debug; до настройки ключа публикация
   невозможна.
3. Адрес API менялся несколько раз; риск старых значений в кэше устройства —
   решается версией конфига и очисткой данных приложения.
4. Доверие невалидному сертификату по `host:port` ослабляет TLS.
5. Полный e2e нестабилен из-за демо-очистки; приёмка — целевыми наборами.
6. Новые залы не получают дефолтные тренажёры автоматически.
7. UI-пагинаторы и restore тренера не реализованы.
8. Redis pub/sub не используется; чат рассчитан на один инстанс backend.
9. Для ОС Аврора нужен отдельный сертификат (ГОСТ) — вне текущего Android-
   релиза.

## 19. История решений (консолидировано)

- Клиент сам выбирает тренера; связь `assignedBy=CLIENT`.
- Замеры веса: тренер (активная связь), ADMIN (любой), ADMINISTRATOR (свой зал).
- Единая пагинация `page/limit` для клиентов, тренеров, тренировок, чатов,
  уведомлений.
- Отчёты агрегируются в PostgreSQL; тяжёлые — только за период.
- Удаление тренера — soft delete; история сохраняется; restore нет.
- `isActive` зала — информационный.
- Redis: распределённый throttler + кеш; чат без pub/sub.
- Пароли: web — сброс ADMIN/ADMINISTRATOR; mobile — смена в настройках.
- Inbox и прочтение — для всех ролей; события тренировок/сообщений/чатов/
  питания с переходом в раздел.
- E2E — отдельная БД `gym_test`; PostgreSQL без `trust`.
- Frontend: code-splitting web, lazy-вкладки mobile, порционная история чата.
- Шаблоны: глобальные/зальные/личные; лимит 10 личных; soft delete.
- Дефолт-конфигурация идемпотентна; идентификация по `defaultKey`.
- HTTPS на nginx web-admin; backend 8080; порт применяется
  `make apply-server`; сертификат — hot reload; отдельный HTTP-порт не
  поднимается.
- Mobile: единый экран просмотра, read-only терминальных статусов, вкладка
  «Тренировки», фильтры, скрытие телефона.
- Release mobile подписывается release-ключом; адрес —
  `https://demogym.staff-rf.ru:3000`.
